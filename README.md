# パーキングルート

目的地（店・施設）を設定すると、その周辺のおすすめ駐車場をレコメンドし、
決めたルートを **Google マップに引き渡す** ルート案内アプリです。

駐車場をレコメンドするかどうかはトグルで選べます。OFF にすれば目的地まで直行のルートになります。

## 公開（GitHub Pages）

`.github/workflows/deploy.yml` が `main` へのプッシュで自動的にビルドしてデプロイします。
型チェックとテストが通らなければデプロイされません。

初回だけ、GitHub 側で 2 つ設定が必要です。

1. **リポジトリを public にする**
   Settings → 一番下の Danger Zone → *Change repository visibility* → Public
   （private のままだと GitHub Pages は有料プランが必要です）
2. **Pages を有効にする**
   Settings → Pages → *Source* を **GitHub Actions** に変更

公開先は `https://<ユーザー名>.github.io/<リポジトリ名>/` です。
サブパス配下で配信されるため、ビルド時に `BASE_PATH` 環境変数でベースパスを渡しています
（ワークフローがリポジトリ名から自動で組み立てます）。

## 使い方

```bash
npm install
npm run dev      # http://localhost:5173
```

APIキーの設定は不要です。そのまま動きます。

## 画面の流れ

1. **出発地を指定（任意）** — 「現在地」ボタン、または検索。設定しておくと目的地検索が現在地の近い順になる
2. **目的地を検索** — 店名・施設名・住所を入れると自動で候補が出る
3. **駐車場をおすすめする（トグル）**
   - **ON** — 「周辺の駐車場を検索」を押すと候補がスコア順に出る。カードか地図のピンで 1 つ選ぶ
   - **OFF** — 駐車場をはさまず目的地まで直行
4. **ルート確定** — 下部のボタンで Google マップを開く

地点検索は入力が落ち着いてから（300ms）自動で走り、打ちながら候補が絞られていきます。
時間のかかる再検索の間も前の候補を薄く表示したままにして、候補が消えないようにしています。
一方、**駐車場の検索は明示的にボタンを押したときだけ**実行します。
絞り込みを変えている途中で何度も Overpass を叩かないようにするためです。

## 地点検索

店名で引けないことが多かったため、多段構えにしています。

**ジオコーダはタイポを許容するので「結果が 0 件かどうか」では当たり外れを判定できません。**
無関係な地点をそれらしく返してくるためです。そこで `matchScore`（名前に検索語が
含まれるか）で当たりを判定し、当たりが出るまで次の順に手を広げます。

1. **Yahoo!・Photon・Nominatim を同時に引く（現在地を優先）**
   Yahoo! ローカルサーチAPI は全国の電話帳データをもとにした独自の店舗情報を持ち、
   Photon（komoot）は POI 名の検索とタイポに強く、Nominatim は住所に強い
2. **名前の合う結果が無ければ、位置バイアスを外して引き直す**
   現在地の近さをかなり強く効かせている（`location_bias_scale=0.1`）ぶん、
   離れた土地の店は上位に出てこない。近所に無いなら全国から素直に探し直す
3. **それでも無ければ、空白を詰めた形 → 語を落とした形へ広げる**
   「肉の天満屋　神楽亭」を、地図データが「肉の天満屋神楽亭」と 1 語で持っている
   ことがある。検索サービスは語の単位で一致を見るため、空白の有無が食い違うと
   当たらない。続いて「台湾鍋　民生炒飯」→「民生炒飯」のように語を落とす
   （屋号だけが登録されていることが多いため）。
   広げるのは当たりが 1 件も無かった場合だけなので、普段の呼び出し回数は増えない
4. **最後に Overpass で名前のタグを直接引く（部分一致）**
   `name` / `name:ja` / `alt_name` を選択和（`台湾鍋民生炒飯|台湾鍋|民生炒飯`）で、
   現在地から 20km 以内。空白を詰めた形も含めるので、丸ごと一致も拾える。
   チェーン店の各支店など、ジオコーダが上位に出さないものを拾う。
   範囲を絞らないと重すぎるため、**現在地が分かっているときだけ使えます**

**正式名称の一部で探せるのはこの 4 段目だけです。** Photon も Nominatim も
語の単位でしか一致を見ないため、「肉の天満屋 神楽亭」を「神楽亭」で引くと
当たらないことがあります。部分一致は Overpass の正規表現に頼るしかありません。

見つからなかったときは、**どの段まで試したかを画面に出します**。
現在地が未設定で 4 段目に進めなかった場合は、「現在地を使って探し直す」を
その場に出し、1 タップで再検索できるようにしています。

集めた結果は **「名前の一致度 → 現在地からの近さ」** で並べ替えます。
距離だけで並べると検索語と無関係な近所の地点が上に来てしまい、
一致度だけだと同名チェーンの遠い支店が上に来るためです。

**入力した名前を含まない地点は、結果として並べません。** ジオコーダはタイポ許容の
ため、「神楽亭」に対して「神楽殿」「神楽橋」のような別物を返してきます。これを
結果に混ぜると、探し物が見つかったように誤解させてしまいます。見つからなかった
ことをはっきり伝えたうえで、「名前が近いだけの候補」として折りたたみで添えます。

検索サービスが応答しなかった場合は、**どのサービスがなぜ落ちたかまで表示します。**
「登録が無い」のか「調べられなかった」のかは利用者にとって意味が違ううえ、
原因を追うにもどれが落ちたかが要るためです。

### Overpass のクエリを重くしない

キーを正規表現で指定する書き方（`[~"^(name|name:ja|...)$"~"..."]`）は名前の索引が
使えず、範囲内の全要素を走査することになります。市街地では確実に時間切れになるため、
**キーを 1 つずつ指定**して索引を効かせています。半径も 20km にとどめています。

どれか 1 つのサービスが落ちても、残りの結果は返します。

### 現在地の使い方

現在地が分かっていると、両サービスに位置バイアスを渡し（Photon は `lat`/`lon` と
`location_bias_scale=0.1`、Nominatim は `viewbox`）、結果も近い順に並べて距離を表示します。

基準点は **出発地が設定されていればそれ、無ければ端末の現在地**です。
出発地を決めていなくても検索を近所優先にできるよう、両者を切り離しています。

## Google マップへの引き渡し

[Google Maps URLs](https://developers.google.com/maps/documentation/urls/get-started) を組み立てて開きます。
アプリが入っていれば Google マップアプリが、なければブラウザ版が開きます。

| ボタン | ルート | travelmode |
| --- | --- | --- |
| ① 駐車場までの経路を見る | 出発地 → 駐車場 | driving |
| ② 駐車場から目的地までの経路を見る | 駐車場 → 目的地 | walking |
| 駐車場を経由地にして目的地まで | 出発地 → 駐車場（経由）→ 目的地 | driving |
| Google マップで経路を見る（レコメンド OFF 時） | 出発地 → 目的地 | driving |

**いきなり案内は始めず、経路の表示画面で止めます**（`dir_action=navigate` は付けない）。
出発前にルートを確認できるようにするためです。

車で駐車場まで行き、そこから歩く流れは ① → ② の 2 段に分けています。
Google マップの URL は 1 つの経路に 1 つの移動手段しか指定できず、
車と徒歩を混ぜた経路を 1 リンクで表現できないためです。

地点は名前ではなく緯度経度（小数 6 桁）で渡しています。名前で渡すと Google 側の
ジオコーディングで別の同名店舗に解決されることがあるためです。

## レコメンドのしくみ

`src/lib/score.ts` が 4 つの軸を重みづけして 0〜100 のおすすめ度を出します。

| 軸 | 重み | 内容 |
| --- | ---: | --- |
| 近さ | 40 | 目的地からの距離。許容徒歩距離の 2 倍で 0 点 |
| 料金 | 22 | 滞在時間ぶんの概算額で評価（2,000 円で 0 点）。額が読めない場合のみ 無料 > 有料 > 不明 の区分に落とす |
| 停めやすさ | 18 | 構造・車両制限・路面から見積もる（下記） |
| 収容台数 | 10 | 満車リスクの代理指標。100 台で頭打ち |
| 快適さ | 10 | 屋根あり（立体・地下）、24 時間営業 |

### 停めやすさ

**1 台あたりの区画幅は OSM にほとんど登録がなく、直接は測れません。**
代わりに、入れやすさに効く手がかりを重みづけて束ねています。

| 内訳 | 重み | 見方 |
| --- | ---: | --- |
| 構造 | 0.40 | 屋外の平面 1.0 / 屋上 0.75 / 立体 0.7 / 地下 0.6 / 路上の駐車枠 0.15 |
| 車高制限 | 0.25 | 2.1m 以上 1.0 / 1.8m 以上 0.8 / 1.6m 以上 0.5 / それ未満 0.2 |
| 車幅制限 | 0.15 | 2.0m 以上 1.0 / 1.8m 以上 0.7 / それ未満 0.3 |
| 車長制限 | 0.10 | 5.0m 以上 1.0 / 4.7m 以上 0.8 / それ未満 0.4 |
| 路面 | 0.10 | 舗装 1.0 / 未舗装 0.55 |

構造を最も重くしています。単純平均にすると、他の項目が未登録のときに
構造の差が薄まってしまうためです。

**機械式かどうかを示すタグは OSM にありません**（提案止まりで、標準化されていません）。
ただし 1.6m を切る車高制限はまず機械式なので、その代理指標として使っています。

見出し（停めやすい／ふつう／停めにくい）は平均だけでは決めません。
未舗装や低い車高制限のように、それ単体で困る要素があるときは「停めやすい」とは言いません。
平均に埋もれて難点が消えるのを防ぐためです。

### サイズ制限の表示

カードに **車高・車幅・車長** を専用の欄で出します。登録が無い項目は
**「記載なし」**と明示します。表示しないと「制限が無い」と受け取られかねませんが、
実際には**書かれていないだけ**で制限がある駐車場は多いためです。

車種を選んでいる場合、余裕が 5cm 以下の制限には**「ぎりぎり」**と付けます
（ミラーや開扉を考えると、この程度は見ておきたいため）。
入れないと分かっている駐車場はそもそも候補から外しているので、
ここで扱うのは「余裕があるか、ぎりぎりか」だけです。

### 車種の指定

「車種」を選ぶと、**その車が入れないと分かっている駐車場を候補から外します**
（`maxheight` / `maxwidth` / `maxlength` と照合）。制限が未登録の項目は
判断材料が無いので、入れない扱いにはしません。

軽自動車は幅こそ狭いものの、近年の主力は全高 1.7m 前後あり、
立体駐車場の 1.55m 制限には入りません。高さは車種区分と一致しないため、
区分ごとに実寸で持っています。

### 駐車場の見分け方

`operator` しか無い駐車場は「タイムズ」とだけ表示され、複数並ぶと区別が付きません。
カードには次を添えています。

- **住所**（`addr:*` タグ）
- **目的地から見た方角**（8 方位。20m 以内は方角が定まらないので出しません）
- **運営者**（名前に含まれていない場合のみ）

### 情報の確かさによる割り引き

OSM には `amenity=parking` とだけ書かれた点が大量にあり、住宅の車庫や建物の付属駐車場が
混ざっています。重みづけの点数をそのまま使うと、**実体が駐車場かも怪しい点が「近い」というだけで
上位に来てしまいます**（実際、名称なしの点が 1 位に出ていました）。

そこで重みづけの合計に、次の係数を掛けます。

| 係数 | 条件 |
| --- | --- |
| 0.55 〜 1.0 | 登録情報の充実度。名称・台数・料金・種別・運営者/営業時間の 5 項目が揃うほど 1.0 に近づく |
| × 0.75 | `access=customers`（施設利用者専用）。行き先が違えば停められない |
| × 0.8 | `parking=street_side` / `lane`（路上の駐車枠） |

除外はしません。情報が無いだけで実在する駐車場もあるためです。代わりに順位を下げ、
カードに注意書きを出し、「情報が確かなものだけ」で隠せるようにしています。

### 候補にしないもの

一般の駐車場として案内できないものは、取得の時点で落とします。

- `access`: `private` / `no` / `permit` / `residents` / `employees` / `delivery` など
- `parking`: `private` / `garage_boxes` / `garages` / `carports` / `shed` / `driveway` / `building`
  （住宅の車庫や車庫証明用の区画）
- `parking=bicycle` など、駐輪場が `amenity=parking` で登録されているもの

絞り込み（`ParkingFilters`）はスコアリングの前に適用されます。

- 目的地からの距離（200m〜1200m）
- 駐車時間（30分〜12時間）— 料金の見積もりに使う
- 今すぐ停められる（営業時間内のもののみ）
- 情報が確かなものだけ（充実度 0.4 未満を除く）
- 無料のみ
- 屋根あり
- 車種（軽自動車／コンパクト・セダン／ミニバン・SUV／大型ミニバン）

## 料金の見積もり

`src/lib/fee.ts` が OSM の `charge` / `fee:conditions` タグを解析して、滞在時間ぶんの概算額を出します。
日本の駐車場は表記が揺れるため、次のような書式に対応しています。

| 書式 | 例 |
| --- | --- |
| 金額 / 時間 | `300円/30分`、`￥300 ／ 30分`、`300 JPY/30 min` |
| 時間 → 金額 | `1時間400円`、`30分 200円`、`60分間 400円` |
| ごと・毎 | `30分ごとに200円`、`20分毎 100円` |
| 最大料金 | `最大1,000円`、`上限 800円`、`24時間最大2000円` |

料金は `charge` だけでなく、`charge:conditional`、`fee:conditions`、`fee:conditional`、
`parking:fee`、旧来の `parking:condition:N:charge` にも散っているため、
見つかったものを全部つないで解釈します。金額を含まない条件文（`no @ customers` など）は
料金の手がかりにならないので落とします。

課金は単位時間ごとの切り上げで計算し（30分単位なら 61 分で 3 単位）、最大料金に達したらそこで頭打ちにします。
**読み取れない文字列は推測せず「料金不明」として扱い**、生の文字列をそのまま表示します。

`maxstay`（最大駐車時間）も読み取り、希望の駐車時間がそれを超える場合はカードに警告を出します。

### 自分で登録する料金

OSM に料金が無い駐車場は、カードの「調べた料金を登録する」から手で入れられます。
入力した文字列は上のパーサに通し、以後は OSM 由来のものと同じように概算・並べ替えに使われます。
値は端末の `localStorage` に保存され、次回以降も効きます（`src/lib/feeStore.ts`）。

カードの下段に「🔍 料金を調べる」「✏️ 料金を登録」を並べ、調べてそのまま登録できる形にしています。

### 料金を調べる検索語

`src/lib/webSearch.ts` が検索語を組み立てます。

| 駐車場 | 検索語 |
| --- | --- |
| 三井のリパーク道頓堀第2（固有名あり） | `三井のリパーク道頓堀第2 中央区 宗右衛門町 駐車場 料金` |
| タイムズ（`operator` のみ・住所なし） | `タイムズ 大阪府 大阪市 中央区 宗右衛門町 駐車場 料金` |
| タイムズ（`operator` のみ・住所あり） | `タイムズ 大阪市 中央区 東心斎橋 1-9 駐車場 料金` |
| 駐車場（名称なし） | `大阪府 大阪市 中央区 宗右衛門町 駐車場 料金` |

**「タイムズ」のような運営者名は固有名として扱いません。** それだけではどのタイムズか
特定できないためです（`named` は `name` / `name:ja` タグがある場合のみ true）。
運営者名しか無い駐車場は、代わりに地名を厚く添えて場所を絞ります。

地名は **駐車場自身の `addr:*` タグを優先**し、無ければ目的地の住所で代用します。
固有名があるときは 2 語、無いときは 4 語まで添えます。
名前に既に入っている地名は、重ねても絞り込みが効かないので外します。

固有名が無く運営者名だけの駐車場は、カードにも住所を出します。
「タイムズ」が並んだときに区別が付かないためです。

**Web から料金を自動収集する機能は入れていません。** 静的サイトのため任意のサイトを
ブラウザから取得できない（CORS）こと、そして名前の無い駐車場には照合の手がかりが無く、
誤った金額を出す危険が実利を上回るためです。検索ページを開くところまでを担い、
読み取りと登録は利用者に委ねています。

## 営業時間の判定

`src/lib/openingHours.ts` が `opening_hours` タグを評価し、その時点で営業中かを判定します。
`24/7`、`08:00-20:00`、`Mo-Fr 09:00-18:00; Sa 10:00-16:00; Su off`、`22:00-06:00`（日跨ぎ）、
`09:00-12:00,13:00-18:00`（昼休み）などに対応します。

opening_hours の仕様は非常に大きいため、**確実に読める書式だけを扱い、少しでも怪しいものは「判定不能」として
候補から除外しません**。誤って除外して駐車場を見落とす方が、判定を保留するより害が大きいためです。

一般利用できない駐車場（`access=private` / `no` / `permit`、`parking=private`）は候補から除外します。
同じ駐車場が node と way の両方で登録されている場合は、同名かつ 30m 以内なら 1 件に束ねます。

## 駐車場のデータ源

駐車場は **OpenStreetMap と Yahoo! ローカルサーチの両方**から取り、突き合わせます
（`src/lib/mergeParking.ts`）。得意分野が違うためです。

| | OSM | Yahoo! |
| --- | --- | --- |
| 料金・収容台数・車両制限・構造 | ✅ 一部に登録あり | ❌ 持っていない |
| 固有名・住所 | ❌ 「タイムズ」止まりが多い | ✅ 「タイムズ天満第2」まである |
| 収録数 | 個人経営の駐車場は薄い | 電話帳ベースで厚い |

近接（45m 以内）していて名前が矛盾しないものは同じ駐車場として合成し、
**OSM から仕様を、Yahoo! から名前と住所を**取ります。片方にしかないものはそのまま残します。

業種名（`駐車場` / `コインパーキング`）で裏を取り、「駐車場」という語を含むだけの
別業種（不動産など）は落とします。

Yahoo! 由来の駐車場は、料金や車両制限を持たないぶん登録情報が薄く見えますが、
**電話帳をもとにした情報なので載っている時点で実在は確か**です。
情報の薄さを実在への疑いとして扱わないよう、確からしさに下限を設けています。
代わりに「料金や車両制限は登録がありません」と注意書きを出します。

Client ID が未設定なら Yahoo! は呼ばず、OSM だけで動きます。

## Yahoo! ローカルサーチAPI（任意）

**OpenStreetMap には個人商店が登録されていないことが多く、それが検索の取りこぼしの
主な原因です。** Photon も Nominatim も Overpass も同じ OSM を読んでいるので、
そこに無い店はどれでも見つかりません。

Yahoo! ローカルサーチAPI は独自の店舗データを持つため、この穴を埋められます。
無料で、1 日 5 万件まで使えます。

### 設定

画面の「店舗の検索精度を上げる」を開き、
[Yahoo!デベロッパーネットワーク](https://e.developer.yahoo.co.jp/register)で
発行した Client ID を貼り付けてください。

**Client ID はソースに含めていません。** 公開リポジトリの静的サイトなので、
書けば誰でも読めてしまうためです。入力した ID は**その端末の localStorage
にだけ**保存され、送信先は Yahoo! のAPIだけです。

自分で配信する場合は、ビルド時に `VITE_YAHOO_APP_ID` を渡すこともできます
（ただしバンドルに埋め込まれるため、配信先が公開なら ID も公開されます）。

未設定でもアプリは今までどおり OSM だけで動きます。

### JSONP を使っている理由

Yahoo! のAPIは CORS ヘッダを返さないため `fetch` では読めません。
ローカルサーチAPIは JSONP に対応しているので、`script` タグ経由で取得しています
（`src/lib/jsonp.ts`）。これにより中継サーバを立てずに静的サイトから呼べます。
取得先のスクリプトをそのまま実行することになるため、この方式は Yahoo! に対してだけ使っています。

## データソース

| 用途 | サービス |
| --- | --- |
| 店舗検索（独自データ・任意） | [Yahoo!ローカルサーチAPI](https://developer.yahoo.co.jp/webapi/map/openlocalplatform/v1/localsearch.html) |
| 地点検索（POI・タイポ許容・位置バイアス） | [Photon](https://photon.komoot.io/) |
| 地点検索（住所） | [Nominatim](https://nominatim.org/) |
| 地点検索の最終手段（name タグの直接検索） | [Overpass API](https://overpass-api.de/) |
| 駐車場データ（`amenity=parking`） | [Overpass API](https://overpass-api.de/) |
| 地図タイル | OpenStreetMap |

いずれも OpenStreetMap 由来で、APIキー・課金設定が要りません。

Overpass は取得範囲を絞り込みの徒歩距離に連動させ（`maxWalkM × 1.5`、400〜1500m）、
1 回の応答を 250 件までに制限しています。面積は半径の 2 乗で効くため、
常に最大範囲を取ると市街地では応答が重くなります。同じ場所・同じ半径の再取得は
手元の控えから返します。

本家が混雑して待たされることがあるため、**一定時間（1.2 秒）応答が無ければミラーにも投げ、
先に返った方を採用**します。最初から全ミラーへ一斉に投げれば最速ですが、無償で
公開されているサーバに毎回 2 倍の負荷をかけることになるので、この待ち時間を挟んでいます。検索はボタンを押したときだけ実行するため、
キー入力ごとにリクエストを投げることはありません。Overpass は本家が混んでいるときのためにミラーへ
フォールバックします。

**Google Places API に差し替えたい場合** は `src/api/overpass.ts` の `fetchNearbyParking`
（と `src/api/nominatim.ts` の `searchPlaces`）を同じシグネチャで置き換えれば、UI もスコアリングもそのまま使えます。
Places なら営業中判定や口コミ評価も取れるので、`ParkingLot` に項目を足して `score.ts` の軸を増やす形になります。

## 制約

- 駐車場データは OpenStreetMap の登録内容に依存します。地方や新設の駐車場では登録が薄いことがあります。
- **料金が登録されていない駐車場が多数あります。** 対応タグを広げても、OSM 側に
  そもそも料金が書かれていなければ「料金は未登録」としか出せません。何件中何件が
  分かったかを画面に出し、未登録のものは Google マップで確認できる導線を置いています。
  全件の料金が要る場合は、料金データを持つ商用 API（ナビタイム、ゼンリン等）が前提になります。
- **リアルタイムの満空情報には対応していません。** スコアの「収容台数」はあくまで満車リスクの代理指標で、
  「今その駐車場が空いているか」は分かりません。満空情報を配信しているのはナビタイム、ナビット、
  P-Collection、PPPark! などですが、いずれも法人向けの有償 API です。無料で全国をカバーする
  データ源は存在しないため、必要であればそれらとの契約が前提になります。
- 代わりに **営業時間による「今開いているか」の判定**には対応しています（`opening_hours` タグがある場合のみ）。
- 自分で登録した料金は、その端末のブラウザにだけ保存されます。他の端末や他の利用者には
  共有されません。ブラウザのデータを消すと失われます。
- 料金は OSM に登録された文字列、または自分で登録した内容に基づく概算です。実際の料金体系（平日/休日、夜間料金、提携割引など）
  とは異なる場合があるため、目安として扱ってください。
- 距離は直線距離に 1.3 倍の迂回係数をかけた概算です（分速 80m で徒歩時間に換算）。実際の道路距離ではありません。
